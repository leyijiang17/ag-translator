# ag-translate: OSCAR ↔ Macaulay2 verified code translation

## Why this skill exists, and why it works this way

Macaulay2 and Julia/OSCAR are both real, actively-used systems in algebraic geometry, but they're low-resource languages for an LLM — there just isn't much M2 or OSCAR source in typical training data compared to Python or Java. A direct "translate this" prompt without grounding will produce code that *looks* plausible and is subtly wrong: a renamed function that doesn't exist, a monomial order default that differs, a matrix orientation flipped, or — the sneaky kind — a computation that runs without error but returns a mathematically different object.

Two things make this tractable. First, a curated glossary (`references/toric_glossary.md`) of the actual concept correspondences between the two systems, built from their official docs, gives a grounded first guess instead of a guess from thin training data. Second, and more importantly: algebraic geometry computations are usually *checkable*. A translated script's output has invariants — dimension, degree, a Hilbert basis, whether a group is free — that can be computed in both languages and compared. So instead of trusting a one-shot translation, this skill generates a translation, actually runs both the original and the translation, compares outputs, and repairs mismatches before showing you anything. Treat correctness as something to demonstrate, not assert.

## Overview of the workflow

1. **Figure out direction and locate files.** Determine source language (Julia/OSCAR or Macaulay2) from the file extension or the user's description, and the target language. Locate the source file(s) — could be a `.jl`/`.m2` script or a Jupyter notebook (`.ipynb`).

2. **Check for an existing manifest.** Look for `<target-file>.ag_manifest.json` next to where the output would go. If it exists, this is an **incremental update** — read `references/incremental_translation.md` and follow that protocol instead of starting fresh. This matters a lot in practice: the user's workflow is "add one new computation to my Julia file, get just that new bit translated into the M2 file with the same style as before" — not a full rewrite every time.

3. **Segment the source into logical blocks.** For a notebook, one block per code cell (or a small cluster of cells that clearly form one worked example, if cells are very short and interdependent). For a plain script, blocks are usually blank-line-separated top-level statements, unless the source itself has natural section markers (comments, `##` headers) — use those instead when present, since they usually reflect the author's own logical grouping better than blank lines do.

4. **For each block, translate using the glossary first, live introspection second.** Read `references/toric_glossary.md` and look up the relevant entries before generating anything — it's much faster and more reliable than reasoning from scratch, and it explicitly flags where a straight rename won't work (`IDIOM` rows) or where one side has no equivalent notion (`GAP` rows). For anything the glossary marks `VERIFY`, or anything not covered at all, don't guess — check it live: in Julia, `julia -e 'using Oscar; methods(functionname)'` or `?functionname` at a REPL; in Macaulay2, `M2 -q --no-prompts -e 'apropos "name"; exit'` or `? functionName`. A wrong guess here is exactly the failure mode this skill exists to avoid — the whole point is not shipping a plausible-looking hallucination.

5. **Propose verification checkpoints for the block, before running anything.** For each block, decide what concrete, checkable output would prove the translation is right — a dimension, a degree, a list of generators (order-independent), a boolean predicate, a specific numeric invariant. Write these as short expressions to evaluate in *both* languages. This is a judgment call the skill (you) makes per block, not a fixed rule — some blocks barely need checking (a `rays(C)` call), others are worth checking hard (anything that builds an ideal or a variety). See `references/verification_protocol.md` for how to pick good checkpoints and how to normalize outputs before comparing (ordering, numeric type, etc. genuinely differ between the two systems even when the underlying math is identical).

6. **Run both sides and compare, using the running session so far.** Blocks build on earlier state (a ring or fan defined two cells up gets used five cells later), so run each language as a *cumulative script* — append the new block to everything translated/verified so far in that language, and re-run the whole thing from the top via `scripts/run_julia.sh` / `scripts/run_m2.sh`. This is slower than keeping a live REPL open but avoids an entire class of state-desync bugs, and for realistic notebook-sized inputs the recompute cost is a non-issue. Extract the checkpoint values from each run's output and compare after normalizing.

7. **On mismatch, repair — don't just report.** Feed the diff, both code snippets, and the relevant glossary/doc context back into your own reasoning and try again, up to 3 attempts per block. If it still doesn't verify, don't hide that: include the block in the output with a clear inline comment flagging it as unverified and explaining what didn't match, so the user can look at exactly that spot rather than distrusting the whole file.

8. **Write the output and update the manifest.** Delimit each translated block clearly (see the exact marker format in `references/incremental_translation.md`) so future incremental runs can find and patch individual blocks. Update the manifest with each block's source hash and verification status.

9. **Report a short summary, not a wall of text.** Tell the user, per block or in a compact table: verified / repaired-then-verified / flagged-unverified, and call out anything you had to invent an idiom for (the `IDIOM`/`GAP` glossary cases) since those are the places most worth a second pair of eyes even when the checkpoints passed.

## A few things worth internalizing, not just following

- **The glossary is a snapshot, not ground truth.** It was built from documentation, not from running the software (this was built in an environment without Julia or Macaulay2 installed). Treat every `VERIFY`-tagged row, and honestly any row you're translating for the first time in a session, as worth a quick live check before you lean on it. If you discover the glossary is wrong or outdated during a translation, fix the glossary file too — it should get better over time, not just get used.
- **A `GAP` in the glossary means think, don't force a rename.** The clearest example: Macaulay2's `NormalToricVariety` type is only ever constructed as normal, so there's no `isNormal` predicate — normality is true by construction. If you see OSCAR's `is_normal(X)` in a translation, the right M2 output is not a guessed function call, it's recognizing the object is normal by definition (and saying so).
- **Matrix/vector orientation conventions differ between the two systems** (rows vs. columns for ray generators, points, etc.) in ways that are easy to get backwards silently. When a checkpoint could be sensitive to this (anything involving explicit coordinates), make the checkpoint concrete enough to catch a transposition — compare actual ray/vertex sets, not just counts.
- **Prefer running the real verification loop over skipping it**, even though it's slower than just generating code. That loop is the entire value proposition here over a plain "ask an LLM to translate this" prompt — skipping it for speed defeats the purpose.
- **Prefer a computed check over a hardcoded literal, even when you're confident of the answer for the block in front of you.** The first live test caught this in practice: `is_affine(Y)` was translated as a hardcoded `true` with a correct explanation — fine for that specific cone, but if that block were later copied or edited to use a different fan, the hardcoded answer would silently stop being right while looking untouched. A computed equivalent existed (`#maxCones fan Y == 1` — affine iff the fan has one maximal cone) and should have been used instead. Reserve hardcode-and-comment for cases with no computable equivalent at all (`is_normal`, which is true by construction with nothing to compute) — not for cases where a computed check just takes a little more digging to find.
- **Don't over-trust the `is`-prefix pattern for Macaulay2 predicates.** It holds almost everywhere (`isCartier`, `isSmooth`, `isEmpty`, ...), which makes the one well-known exception easy to miss by analogy: testing whether something is zero is `zero(...)`, not `isZero(...)` — the latter doesn't exist. This exact mistake happened in the first live test, translating `is_principal`'s zero-in-the-class-group check. See the "M2 predicate-naming conventions" section in the glossary.
