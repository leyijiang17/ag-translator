# Verification protocol

## Picking checkpoints

A checkpoint is a small expression, evaluable in both languages, whose value should be identical (after normalization) if the translation is correct. Good checkpoints are:

- **Cheap to compute** relative to the main computation — don't add a second Gröbner basis computation just to check the first one; ask for something like `dim`, `degree`, or a count instead when possible.
- **Insensitive to irrelevant choices.** Some outputs are canonical (dimension, degree, Betti numbers, a group being free or not, a boolean predicate) — compare these directly. Others are legitimately choice-dependent even when correct (explicit Gröbner basis generators depend on monomial order and algorithm; explicit free resolution differentials aren't unique) — for these, check a canonical derived quantity instead (e.g., "the ideal generated by both bases is the same ideal" rather than "the generator lists are textually identical").
- **Specific enough to catch real bugs**, not just crashes. "Both sides ran without error" is not a checkpoint. If a block builds a cone from explicit coordinates, check the actual ray set (not just `dim` or a count), because that's exactly where a row/column transposition bug would hide.

Roughly one checkpoint per block is often enough; blocks that construct a new mathematical object (a ring, ideal, variety, divisor) deserve one, blocks that only inspect an already-checked object (printing rays you already verified) often don't need a fresh one.

## Normalizing before comparing

Outputs from the two systems will differ in superficial ways even when mathematically identical:

- **Ordering**: sets of generators, rays, or vertices may come back in different orders. Sort before comparing, or compare as sets/multisets rather than sequences.
- **Numeric representation**: exact rationals vs. different internal representations, or a boolean printed as `true`/`false` vs. `true`/`false` with different capitalization conventions in output text. Parse into a real Julia/M2-independent value (Python int/Fraction/bool once you're comparing programmatically, or just careful reading) rather than string-comparing raw output.
- **Coordinate/orientation conventions**: rays-as-rows vs. rays-as-columns, 0- vs. 1-indexing. If a checkpoint could be sensitive to this, make sure the comparison would actually fail on a transposed answer — comparing only a count or a dimension can silently pass even when the concrete data is wrong.
- **Group representations**: a class group or Picard group might come back as a module presentation, a list of invariant factors, or an abstract description depending on the call. Compare a derived, unambiguous property (rank, torsion-freeness, order) rather than raw presentations unless you've confirmed both sides use the same representation.

## The repair loop

When a checkpoint mismatches:

1. Look at both raw outputs and the diff, not just "pass/fail."
2. Reconsider: is this actually a translation bug, or is it a normalization problem (the checkpoint compared things that don't need to be identical)? Fix the checkpoint if the latter.
3. If it's a real bug, check the glossary entry for that operation again — is there an `IDIOM` or `GAP` note you missed, or a `VERIFY` flag you should now resolve with a live introspection check?
4. Regenerate the block's translation with this context and re-run.
5. Cap at 3 attempts per block. After that, stop trying to force it — flag the block clearly in the output instead. A visible "this didn't verify, here's what mismatched" is much more useful to the user than a fourth guess that might look right by accident.

## What "verified" means in the summary

Be precise in the final report:
- **Verified**: translated on the first attempt, checkpoints matched.
- **Repaired**: needed 1-3 attempts, but checkpoints matched in the end — still worth a one-line note on what was wrong, since it's a sign the glossary might need updating.
- **Unverified / flagged**: didn't converge in 3 attempts. Included in the output with an inline comment, but the user should look at it before trusting it.
- **Not checked**: a deliberate call that a block didn't need a checkpoint (e.g., it only re-displayed an already-verified object). Say so explicitly rather than letting it look identical to "verified."
